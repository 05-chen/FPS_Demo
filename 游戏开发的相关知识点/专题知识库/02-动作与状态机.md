# 02-动作与状态机

## 1. 动作系统的本质

动作系统不只是“人物会跑、会跳、会攻击”，而是：

- 输入是什么
- 当前状态是什么
- 是否允许切换
- 是否有过渡条件
- 是否与动画、物理、网络互相协调

如果这些关系不清晰，角色就会出现：

- 动画卡住
- 输入被吞掉
- 状态串联
- 动作切换异常
- 角色看起来像“卡住了”

---

## 2. 状态的重要性

一个角色通常至少有：

- Idle
- Move
- Jump
- Fall
- Attack
- Reload
- Hurt
- Dead
- Respawn

状态机的意义：

- 让行为可控
- 让切换条件明确
- 让输入和动作解耦
- 让调试更容易

如果不用状态机，代码很快变成：

- 一大堆 if / else
- 枝叉越来越多
- 逻辑很难维护
- 触发顺序很难控制

---

## 3. 输入与状态的分离

### 推荐设计

- 输入层：检测按键和鼠标操作
- 状态层：决定当前应该是什么状态
- 动作层：执行移动、攻击、重力等逻辑
- 动画层：播放对应动画

### 常见错误

- 输入直接调用攻击函数，导致状态和动画混在一条逻辑链里
- 动画参数在错误时机更新，导致状态切换异常
- 角色处于 Attack 状态，却还能执行 Move 或 Jump

---

## 4. 状态切换规范



### 状态切换应该遵守

- 哪些动作可以打断当前状态
- 哪些动作不能打断
- 进入新状态前是否清理旧状态
- 离开当前状态时是否关闭碰撞/事件/动画参数



### 典型状态例子



#### Idle → Move

- 需要输入有效
- 不能处于攻击、死亡等状态



#### Move → Jump

- 在地面状态下允许
- 需要条件: 可跳跃、未死亡



#### Attack → Hurt

- 可以打断，但需要判断是否允许被打断



#### Hurt → Dead

- 生命值<=0 时进入死亡状态

---



## 5. 动画和逻辑的分层



### 动画层

- 负责角色视觉表现
- 通过参数驱动状态动画



### 逻辑层

- 负责状态变化、速度、位置、技能检验



### 关键原则

- 动画不应该直接决定逻辑事实
- 逻辑不应该假设动画已经完全播放结束
- 最好有一个明确的“状态名”作为中间桥梁

---



## 6. 动作系统调试建议



### 重点观察

- 当前状态是什么
- 输入是否成功进入状态
- 能否退出当前状态
- 动画参数是否变化
- 是否重复进入同一个状态



### 调试工具建议

- AnimatorDebugger
- PlayerStateLogger
- StateTransitionLog

---



## 7. 常见动作问题



### 1. 角色卡在某个状态里

- 检查状态切换条件
- 检查是否缺少退出条件
- 检查是否动画过渡失败



### 2. 输入无效

- 看是否状态不允许执行该动作
- 看是否输入在错误时机被吞掉
- 看是否被其他状态覆盖



### 3. 动画与逻辑不一致

- 看是否动画状态和真实状态脱节
- 看逻辑是否直接依赖动画事件
- 看是否在不同更新阶段造成不一致

---



## 8. 状态机模板

```csharp
public enum PlayerState
{
    Idle,
    Move,
    Jump,
    Attack,
    Hurt,
    Dead
}

public class PlayerStateController
{
    public PlayerState currentState;

    public void TransitionTo(PlayerState nextState)
    {
        if (currentState == nextState) return;
        currentState = nextState;
        Debug.Log("State changed to: " + nextState);
    }
}
```

---



## 9. 实战建议



### 你做角色时最好先明确

- 角色有哪些动作
- 哪些动作能中断
- 哪些动作不能中断
- 哪些动作必须在服务器确认
- 哪些动作只在本地表现

这是动作系统设计的核心。
